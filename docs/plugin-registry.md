# Plugin Registry и жизненный цикл

PluginManager объединяет источники манифестов, каталог блоков, конфигурацию
и загрузчик. При чтении каталога встроенный источник ищет
`bot/blocks/*.plugin.toml`. Манифест указывает класс, метаданные, начальное
состояние и дополнительные callback-действия. Для встроенного блока
entry point ссылается на Python-модуль с таким же именем, как файл манифеста.

Пример кода и соответствующего манифеста есть в [Plugin API v1](plugin-api.md).

## Запуск и состояния

1. Реестр сохраняет описания найденных блоков и результаты проверки манифестов.
2. PluginConfig читает `[blocks]` из `blocks.toml`. При создании файла бот
   использует `blocks.toml.example`, а для отсутствующих в шаблоне ключей
   берёт `default_enabled` из манифеста. В существующем файле новые ключи
   добавляются выключенными. Ключи отсутствующих блоков сохраняются.
3. Загрузчик импортирует только выбранные блоки с корректными манифестами.
   Метаданные и список `extra_actions` класса должны совпадать с манифестом.
   У блока свой PluginContext и NullBroker. SystemMonitor и AlertManager общие.
4. Менеджер выполняет `setup()` всех загруженных блоков и затем `start()`
   подготовленных. Хуки ограничены по времени, если возвращают управление
   циклу событий. Ошибки импорта, конструктора и хуков видны в записи блока
   и журнале. При ошибке подготовки или запуска у созданного экземпляра
   вызывается `stop()`.
5. Telegram-команды, кнопки и фоновые проверки регистрируются для
   запущенных блоков. Недоступность системной зависимости отмечается
   отдельно. Блок может показать собственную диагностику.
6. При завершении бот прекращает фоновый опрос и приём обновлений,
   затем менеджер останавливает блоки в обратном порядке. Сбой одного
   `stop()` сохраняется в реестре, остальные блоки завершаются штатно.

`enabled` отражает настройку файла. `PluginState` хранит состояние
`DISCOVERED`, `LOADED`, `READY`, `RUNNING`, `STOPPED` или `FAILED`.
`PluginHealth` хранит отдельную оценку от `UNKNOWN` до `HEALTHY`,
`DEGRADED` или `UNAVAILABLE`. Блок с отсутствующей внешней зависимостью
может одновременно быть `RUNNING` и `UNAVAILABLE`. В реестре доступны
последняя ошибка и описание проблемы с зависимостью.

`python main.py --check-blocks` проверяет конфигурацию, загрузку и зависимости
включённых блоков. Он завершится с кодом 1 при ошибке и укажет ID блока.
Проверка работает без подключения к Telegram и без вызова хуков.

## Программное управление конфигурацией

Методы каталога и переключателей доступны без настроек Telegram, сетевого
соединения и импорта Python-модулей блоков.

```python
from pathlib import Path

from bot.plugins.config import PluginConfig
from bot.plugins.manager import PluginManager
from bot.plugins.sources import BuiltinPluginSource

manager = PluginManager(
    sources=[BuiltinPluginSource()],
    config=PluginConfig(Path("blocks.toml"), Path("blocks.toml.example")),
)
manager.discover()
for record in manager.list_plugins():
    print(record.plugin_id, record.enabled, record.state.name)

manager.disable("docker")
```

`enable()` и `disable()` записывают конфигурацию. При следующем запуске
меняется состав активных блоков. Запись использует файловую блокировку,
сверку с исходным содержимым и атомарную замену. Для обычной таблицы
`[blocks]` редактирование сохраняет порядок и комментарии. Необычные
формы TOML, например inline-таблица, при необходимости приводятся к
обычной таблице.

Состояния жизненного цикла относятся к текущему процессу. Отдельный
процесс управления видит собственный реестр и сохранённые переключатели.
Проверки зависимостей работают в потоках. Тайм-аут ограничивает ожидание,
а уже начавшийся синхронный вызов может завершиться позднее.
