# Архитектура блоков

## Исходное состояние перед Plugin API v1

В исходной ветке main доступны девять блоков. CrowdSec находится в ветке
codex/crowdsec. При запуске бот обнаруживает классы в bot/blocks, читает
переключатели из `[blocks]` в blocks.toml и создаёт экземпляры включённых
блоков. Раньше конструктор каждого блока получал общие экземпляры SystemMonitor
и AlertManager. Имена команд, подписи и признаки уведомлений хранились
в атрибутах класса.

| Блок | Данные и зависимости | Поведение |
| --- | --- | --- |
| `cpu` | `get_cpu_metrics`, `check_cpu_alert`, графики и форматирование | Потребление по ядрам, график, сводка, порог CPU |
| `memory` | `get_memory_metrics`, `check_memory_alert`, графики и форматирование | ОЗУ и swap, график, сводка, порог памяти |
| `disk` | `get_disk_metrics`, `get_all_disk_metrics`, `check_disk_alert` | Список файловых систем, сводка корневого раздела, порог диска |
| `network` | `get_network_metrics`, форматирование | Трафик, пакеты и ошибки интерфейсов, кроме loopback |
| `top` | `get_top_processes`, лимит процессов, графики | Сводка самого активного процесса и список процессов |
| `temp` | `get_temperature`, форматирование | Датчики и их пороги, максимальная температура в сводке |
| `uptime` | `get_uptime_info`, форматирование | Время работы, последняя загрузка, пользователи |
| `services` | `get_services_status` через systemctl | Список активных и неактивных служб |
| `docker` | Docker SDK, доступ к сокету Docker, клавиатуры | Сводка, список с пагинацией, детали, запуск, остановка и перезапуск контейнеров |
| `crowdsec` | cscli, опциональный `sudo -n`, `create_custom_alert` | Сводка LAPI, детали событий, уведомления о новых событиях |

Команды и кнопки доступны только для включённых блоков. Маршрутизация
проверяет авторизацию и распознаёт устаревшие кнопки выключенных блоков.
Интерфейс блоков использует MarkdownV2. Измерения, рендеринг и проверки
уведомлений выполняются в рабочих потоках. HealthMonitor отправляет
результаты проверок разрешённым адресатам, а AlertManager ведёт историю
и контролирует интервалы между пороговыми уведомлениями.

## Plugin API v1

Ядро использует метаданные для команд, меню и подключения уведомлений.
На каждый включённый блок создаётся отдельный PluginContext. SystemMonitor
и AlertManager реализуют соответствующие протоколы напрямую, поэтому
блоки используют общее состояние уведомлений и настройки порогов.
На втором этапе [Plugin Registry](plugin-registry.md) читает манифесты,
сопоставляет их с `[blocks]` и загружает выбранные классы.

```text
Telegram → команды и кнопки → Block → BlockView
                                  ↓
                            PluginContext
                         ↙       ↓       ↘
               SystemProtocol   AlertProtocol   BrokerProtocol
                         ↓       ↓       ↓
                 SystemMonitor  AlertManager  NullBroker
```

Бот вызывает `setup()` и `start()` до начала опроса Telegram и запуска
мониторинга. При остановке сначала прекращается опрос и планирование
уведомлений, затем вызывается `stop()` в обратном порядке подготовки.
Если запуск прерывается внутри блока, завершение вызывается и для этого
блока. Проверка `--check-blocks` создаёт включённые блоки и проверяет
их зависимости без запуска хуков.

Описание методов и пример блока есть в [Plugin API v1](plugin-api.md).
