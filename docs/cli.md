# lsab

CLI управляет встроенными блоками Linux Server Admin Bot. Команды каталога
и диагностики работают без Telegram-токена и соединения с Telegram.
Диагностика Docker проверяет локальную службу с правами
пользователя, который запустил CLI.

## Установка и запуск

Нативный установщик добавляет команду `.venv/bin/lsab`. Из существующего
окружения в корне проекта можно установить команду отдельно.

```bash
python -m pip install --no-deps -e .
lsab plugins list
```

Для запуска из исходников используйте `python -m cli`. В Docker-образе
команда `lsab` также доступна. Для управления Compose запускайте CLI
на Docker-хосте.

По умолчанию CLI использует `blocks.toml` из рабочей копии. Для установленного
пакета вне рабочей копии путь берётся из текущего каталога. Явный путь
`--config` имеет приоритет над `BLOCKS_CONFIG`. Глобальные флаги ставятся
перед командой.

## Блоки и диагностика

```bash
lsab plugins list
lsab --json plugins info docker
lsab plugins enable cpu memory disk
lsab plugins disable docker network --dry-run
lsab plugins check
lsab plugins doctor docker
lsab plugins configure
```

- `list` и `info` читают манифесты. `info` дополнительно показывает состояние
  экземпляра, если доступен свежий статус.
- `check` проверяет конфигурацию и зависимости включённых блоков.
  `doctor <id>` может импортировать конкретный выключенный блок и проверяет
  его манифест, совместимость, загрузку и системные зависимости.
- `enable` и `disable` записывают всю группу переключателей одной операцией.
  Превью `--dry-run` показывает будущие значения без записи на диск.
- В `configure` стрелки выбирают блок, пробел меняет его состояние,
  **A** включает все, **N** выключает все, **S** сохраняет, **Q** отменяет.
  Описание выбранного блока видно внизу. Для управляемой службы после
  сохранения CLI предлагает подтвердить перезапуск. Если Python собран
  без `curses`, CLI использует ANSI-терминал и стандартный модуль `termios`.

Изменения сохраняются в исходном TOML с комментариями и порядком. CLI
проверяет, что конфигурация не изменилась во время интерактивного редактирования.
Старая команда `python main.py --check-blocks` также доступна.

## Служба и реальное состояние

```bash
lsab status
lsab logs --follow
lsab version
lsab doctor

lsab --service systemd restart
lsab --service docker status
lsab --service docker --compose-file docker-compose.yml logs --follow
```

`auto` выбирает установленную пользовательскую службу
`linux-server-admin-bot.service` или ручной режим. `systemd` использует
`systemctl --user` и `journalctl --user`. `docker` использует Docker Compose
и по умолчанию читает `data/config/blocks.toml` в каталоге проекта.
Для ручного запуска CLI показывает фактический статус и читает стандартный
журнал `logs/bot.log`. Запуском и остановкой управляет терминал бота.

`--project-dir` задаёт рабочую копию для поиска конфигурации и файлов Compose.
`--compose-file` можно передать несколько раз. `--verbose` включает
дополнительную диагностику в stderr, а `--json` выводит данные в JSON.
Текстовый вывод по умолчанию без цвета. `logs --follow` и TUI работают
в текстовом режиме.

Бот атомарно публикует статус рядом с конфигурацией в
`.lsab/<имя файла>/status.json`. CLI сверяет время обновления, PID
и идентификатор процесса Linux. Состояние конфигурации может отличаться
от фактического состояния уже запущенных блоков. Статус содержит хеш
применённого файла, версию, отметки времени и категории состояния.
Последний снимок конфигурации текущего процесса хранится отдельно
с ограниченными правами доступа. В Compose каталог доступен через общий
bind mount. Для проверки PID используется штатный `pid: host` проекта.

## Применение и откат

```bash
lsab --service systemd plugins apply
lsab --service systemd plugins enable disk --apply
lsab plugins rollback
lsab --service systemd plugins rollback --apply
```

`apply` проверяет выбранный файл и зависимости, затем перезапускает
службу. CLI ждёт свежий отчёт именно от нового процесса с ожидаемым
хешем и здоровыми включёнными блоками. Ошибка проверки оставляет службу
работать с предыдущими настройками. Если запуск с новой конфигурацией
сорвался, CLI восстанавливает предыдущий файл и проверяет повторный
запуск. Если восстановление тоже не удалось, CLI сообщает обе ошибки
и возвращает ненулевой код.

Если служба уже запущена, для первого `apply` нужен её свежий отчёт
или сохранённый снимок успешно применённой конфигурации. После обновления
со старой версии запустите службу с этой версией до первого применения.
CLI хранит последний успешно применённый файл и до пяти предыдущих
снимков в каталоге `.lsab/<имя файла>/`. `rollback` восстанавливает
предыдущую версию файла. Для применения восстановления к службе укажите
`--apply`. Для Docker требуется доступ к настроенному Docker daemon.

Диагностика брокера и просмотр разрешений описаны в [Privilege Broker](privilege-broker.md).
